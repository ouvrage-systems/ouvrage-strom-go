## 1. Executive Summary & Context

To maximize modularity, reduce dependency debt, and prepare Ocalque for its initial `v0.1` release, we officially extracted the serialization and streaming container engine into a standalone repository: **Ouvrage-Strom** (`github.com/ouvrage-systems/ouvrage-strom-go`).

During this session, we:
1. Initialized the new `ouvrage-strom-go` Go module.
2. Refactored the core library (retaining the code prefix/alias `ostrom`) to be 100% generic (removing hardcoded compiler bindings).
3. Drafted the architectural blueprints to transition Ostrom from a static, passive stream archive into a stateful, reactive execution engine.

---

## 2. Decoupling Ostrom Core from Ocalque

The original implementation of `ostream` was coupled to Ocalque through hardcoded checks inside `GetPayloadCount()`, which implicitly mapped compiler-specific kinds (like `Calque` or `SymbolTable`) to payload numbers.

To resolve this, we introduced the **Kind Registry pattern**:
* **The API**:
  ```go
  var kindPayloadCounts = make(map[string]int)

  func RegisterKind(kind string, count int) {
      kindPayloadCounts[kind] = count
  }
  ```
* **How Ocalque Integrates**: Ocalque now registers its custom kinds during CLI startup:
  ```go
  ostrom.RegisterKind("Calque", 3)
  ostrom.RegisterKind("CalqueInterface", 1)
  ostrom.RegisterKind("SymbolTable", 1)
  ```
* **Result**: The Ostrom library is now completely domain-agnostic and ready for reuse in non-Ocalque systems (e.g., telemetry logs, documentation packaging, general-purpose multi-payload streams).

## 3. Design Proposals for Ostrom v2: The Active Stream

We outlined three key concepts to evolve the streaming engine into a stateful, event-sourced runtime engine:

### 3.1 Event-Driven Handlers vs. Payload Transforms
We decouple high-level orchestration from local data mutations:
* **Resource Handlers (Stream Level)**: Registered programmatically by the consuming application. They listen to resource lifecycle events (e.g. matching specific Kinds or tags) and manage stream-level operations (altering envelopes, muting/skipping resources, or emitting new ones).
* **Payload Pipelines (Data Level)**: Declared by the template author inside the resource spec (`spec.stages.<stage_name>.pipeline`). They apply a sequential chain of pure, isolated, byte-to-byte transformations (e.g., regex `Replace`, AST-level edits, format converters) directly to raw payloads.

### 3.2 Shared Key-Value Context & Artifact Store
* **Keystore**: A lightweight, memory-backed Key-Value store to share variables and configs across resources (e.g., secrets populated JIT).
* **Artifact Store**: A storage service to exchange heavy payloads generated by prior stream resources (e.g. saving a JSON list of verified container digests).

### 3.3 Deferred Evaluation & Promises
To enable single-pass, sequential stream parsing in $O(1)$ memory even when resources have out-of-order dependencies:
* A resource can register a "promise" on a payload identifier that appears later in the stream.
* The execution engine suspends evaluation of that resource and automatically resolves the promise as soon as the target payload passes through the `Scanner`.

## 4. The Declarative Schema Layer & Static Validation

To prevent runtime failure in complex stream pipelines, we designed a **Declarative Schema Layer** separating interface declarations from data payloads:

### 4.1 Resource Interfaces (`ResourceInterface`)
Instead of duplicating input/output schemas in every resource instance, the stream defines contracts at the schema level:
* **Dynamic Registration**: Declared as early stream control resources (`kind: ResourceInterface`) or programmatically registered via Go API:
  ```yaml
  apiVersion: ostrom.ouvrage.io/v1
  kind: ResourceInterface
  spec:
    targetKind: Calque
    consumes:
      keystore: ["secret.db_password"]
      artifacts: ["artifact.docker_digest"]
    produces:
      artifacts: ["artifact.k8s_manifest"]
  ```

### 4.2 Two-Pass Stream Compiler
Ostrom compiles and executes streams in two sequential passes:
1. **Pass 1: Static Linking & Verification**: The engine reads only `ResourceInterface` headers and resource envelopes. It builds a directed acyclic graph (DAG) of all stream bindings (inputs/outputs) and fails fast if any required variable or artifact is missing.
2. **Pass 2: Event-Sourced Execution**: The stream executes with 100% guarantee of contract integrity.

---

## 5. Security Audits & Access Control Policies (ACLs)

By enforcing static visibility on resource interfaces, Ostrom opens the door to **fine-grained security auditing and sandboxing**:
* **Least Privilege Enforcement**: The Ostrom runtime engine inspects the resource contracts to restrict system privileges dynamically.
* **Access Control Lists (ACLs)**: If a resource handler (e.g. an Ansible deployment handler) tries to open a network port or access Docker socket privileges, but its `ResourceInterface` contract did not declare these capabilities, the engine blocks the execution immediately.
* **OpenAPI Schema Exports**: The CLI will support exporting the entire stream interface registry to OpenAPI schemas for compliance auditing (e.g. verifying NIS2, DORA, and ISO 26262 security boundaries at compile-time).

---

## 6. Day 0 Design Stance

This architectural model is highly ambitious, providing a unified, secure, and event-sourced alternative to traditional CI/CD pipelines and shell scripting. 

Because of the complexity and security implications of this schema design, we made a conscious choice to **keep the `ouvrage-strom-go` repository clean of any raw, fragile code**. The repository is initialized as a blank whiteboard (`cmd/`, `internal/`, `pkg/`) so we can iteratively debate and stabilize the Ostrom v2 specification before committing to code implementation.
